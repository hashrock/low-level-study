    解説
    
        
    なぜ Promise.then は setTimeout(0) より先に走るのか
    
        
    イベントループの 1 周は「マクロタスクを 1 個実行 → マイクロタスクキューが空になるまで全部実行」の繰り返し。
          メインスクリプトそのものが最初のマクロタスクで、setTimeout(f, 0) は f をタイマーヒープに入れるだけ。f は「次以降のマクロタスク」として、ループが次に何を実行するか選ぶときに初めて取り出される。
    
        
    一方 Promise.resolve().then(g)・await の続き・queueMicrotask(g) はマイクロタスクで、今のタスクが終わった直後、ループに制御が戻る前に流される。だから遅延 0 でもタイマーは必ず後。
          タイマーのコールバックの中で作った Promise も、次のタイマーより先に走る（timers.js の 7 番）。
    
        
    minirt では、goja がジョブキューを内部に持ち、JS から Go へ最外周で戻るとき（Runtime.leave()）に空になるまで流す。ループが実行するタスク（メインスクリプト・タイマー・op 完了での resolve()）は全部この「最外周の呼び出し」なので、何もしなくても HTML/Node と同じ順序になる。
          「1 タスク」ボタンでこの単位で進み、「1 イベント」でその中身（キューへの出入り）を 1 つずつ見られる。
    
        
    この可視化の「近似」について（正直に）
    
        
      
          
    • タスク・タイマー・非同期 op はランタイム自身のものなので正確。
      • 
          
    • マイクロタスクは goja 内部のキューにあり「キューに入った瞬間」のフックが無い。代わりに goja の AsyncContextTracker（反応の登録時と、ハンドラの実行直前・直後に呼ばれる）と、Promise.prototype.then の差し替えで観測している。
      • 
          
    • queueMicrotask と「解決済み Promise への .then」は登録＝キュー投入なので正確。未解決の Promise への .then は「待機中」と表示し、Promise が解決したことは次に制御が戻った時点（次のジョブの直前など）で気付いて「キュー済み」に移す。順番は正しいが瞬間は少し遅れる。
      • 
          
    • await は goja が内部の then を直接呼ぶので、待っている Promise が見えない。「await（状態不明）」として表示し、実際に走った時点で確定する。await null のように実際はすぐキューに入っているものも含む。
      • 
          
    • ユーザーのハンドラを呼ばない内部ジョブ（thenable の解決など）は見えない。.catch(f) の成功側のようにハンドラが無い反応は、タスク終了時に「破棄」として消す。
      • 
          
    • 行番号は .then / queueMicrotask の呼び出し位置。await は goja が関数の先頭位置しか返さないため関数名だけ。
      • 
        
    
        
    パーミッションとパスの正規化
    
        
    許可ディレクトリは起動時に正規化し、要求パスはカーネルと同じ順序（シンボリックリンクを先に辿り、.. は辿った後のディレクトリに適用）で解決してから「許可ディレクトリと等しいか dir + "/" で始まるか」を判定する。
          sandbox_escape.js を実行すると、examples/data/../../go.mod が /app/go.mod、examples/data/link_to_etc/passwd が /etc/passwd に正規化されて拒否される様子がログに出る。
          正規化後のパスはホスト側のログにだけ表示し、スクリプトに返すエラーメッセージには入れない（リンク先を教えないため）。
    
        
    脅威モデルと限界（README §5 より）
    
        
      
          
    • メモリ枯渇は防げない：goja は Go のヒープに確保し、上限で止める仕組みが無い。本当に必要ならプロセス分離（rlimit / cgroups）。
      • 
          
    • CPU は壁時計の上限だけ。命令数の制限は無い。組み込み関数（巨大な repeat・JSON.parse・正規表現の破滅的バックトラッキング）の中にいる間は vm.Interrupt が効かず、タイムアウトが遅れる。
      • 
          
    • TOCTOU：検査と open の間に途中のディレクトリを差し替えられる競合は防げない（O_NOFOLLOW は最終要素だけ）。ハードリンクもパス検査では防げない。
      • 
          
    • ネットワークはホスト名ベース：DNS rebinding で内部 IP に向けられても通る。リダイレクトの各ホップは再検査している。
      • 
          
    • 同一プロセスで動くので、エンジンやランタイムのバグはそのままホストの権限で動く。op 数・出力量・タイマー数にも上限が無い。Date.now() の精度も落としていない。
      • 
        
    
        
    ブラウザ版での違い
    
        
      
          
    • ブラウザ自体がサンドボックスなので、ここでの「隔離」は教材としての意味しかない。ファイルはメモリ上の仮想 FS、fetch は決まった URL だけ答える偽ネットワーク、環境変数も偽物。
      • 
          
    • 時計は仮想時刻：やることが無くなると次の期限まで一気に進むので、何度実行しても同じ順序になる。Date.now() も仮想時刻を返す。op の処理は開始時にその場で行い、結果を「開始時刻 + 遅延」に届ける（CLI では goroutine で実行）。
      • 
          
    • js/wasm はシングルスレッドで goroutine のプリエンプションが無いため、for(;;){} の最中に vm.Interrupt を呼ぶ goroutine が動けない。そこでランタイム全体を Web Worker で動かし、応答が無ければ Worker ごと終了する（CLI の終了コード 124 に相当）。
